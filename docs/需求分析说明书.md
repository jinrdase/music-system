# 潮流音乐专辑及衍生品发售系统需求分析说明书

## 1 概述

### 1.1 编写目的

本文说明 music-system 的建设目标、使用角色、功能边界和质量要求，作为项目设计、开发、测试和答辩的依据。本文内容以当前项目实际代码、接口和数据库为准；对尚未实现或未验证的能力单独标注，避免把规划写成既有功能。

### 1.2 项目范围

系统面向音乐消费者和后台运营人员，提供数字专辑及实体衍生品的展示与交易能力。用户能够浏览专辑和歌曲、管理购物车与收货地址、创建订单、进行开发环境模拟支付、查询物流、申请退款以及购买盲盒。管理员能够维护专辑、歌曲、盲盒和用户，处理订单发货与退款审核，并查看操作审计。

本项目采用浏览器访问的前后端分离方式。前端负责界面和交互，后端负责认证、权限、业务规则和数据持久化。真实支付宝交易需要商户侧密钥、回调地址等外部配置；当前演示优先使用模拟支付。

### 1.3 术语

| 术语 | 说明 |
|---|---|
| 数字专辑 | 通过订单授权用户访问数字内容的商品形态 |
| 实物商品 | 需要收货地址、发货和物流信息的商品 |
| 盲盒 | 用户购买抽取次数，支付成功后由服务端抽取奖品的商品 |
| JWT | 登录后由服务端签发、请求时用于身份认证的令牌 |
| QA 数据 | 用于本地测试、可识别且不代表真实交易的数据 |

### 1.4 运行环境

| 类别 | 当前项目配置 |
|---|---|
| 后端 | Java 17、Spring Boot 4.0.8、Maven |
| 数据访问 | MyBatis-Plus 3.5.17 |
| 数据库 | MySQL 8.x；本地开发连接端口为 3307 |
| 缓存与并发 | Redis、Redisson 3.35.0 |
| 身份认证 | JJWT 0.12.6、JWT_SECRET 环境配置 |

## 2 用户角色与权限

### 2.1 普通用户

普通用户注册、登录后可以访问个人数据和交易功能。订单、地址、购物车、退款与抽取记录均按当前登录用户隔离。用户只能操作本人拥有的订单和地址。

### 2.2 管理员

管理员可以进入后台管理页面并调用被授权的管理接口。后端按角色执行授权；超级管理员拥有更高权限，例如用户角色变更。前端路由守卫只用于改善导航体验，不构成安全控制。

### 2.3 未登录访问者

注册、登录以及配置中明确放行的少数端点可以不带 Token。当前项目的 `/api/**` 大部分接口受 JWT 拦截；专辑目录接口也应按当前拦截配置理解为需登录访问。

## 3 业务流程

### 3.1 普通商品交易

用户登录后浏览专辑，查看商品形态、价格、库存和曲目信息；选择商品及收货信息后创建订单。后端再次验证用户、地址、商品状态和库存，保存订单快照并预留库存。用户完成模拟支付或配置好的支付后，订单进入已支付状态。实物订单由管理员发货，用户确认收货；符合条件的订单可申请退款。

### 3.2 盲盒交易

用户查看上架盲盒及奖品配置，选择单抽或十连抽并选择本人地址，创建待支付盲盒订单。创建订单时服务端校验库存并预留库存，但不产生抽奖结果。支付成功后服务端执行抽取、保存结果和保底统计。前端没有直接决定奖品的接口调用。

### 3.3 管理流程

管理员登录后查看后台数据，维护专辑、歌曲和盲盒信息，管理用户及订单，填写物流信息、审核退款，并查询重要管理操作的审计记录。所有管理请求均由服务端重新校验身份与角色。

|---|---|---|---|
| F-01 | 账户认证 | 注册、登录、获取个人资料、修改个人信息/密码、退出 | 后端用户接口、JWT 拦截器及前端登录状态管理 |

| F-08 | 退款 | 用户申请、查看本人申请，管理员审核 | 按商品类型、订单状态和数字内容访问情况校验 |

| F-10 | 后台商品管理 | 管理专辑、歌曲和盲盒，支持已有接口提供的查询、编辑和媒体操作 | 每项操作需以对应 Controller 现有方法为准；不宣称不存在的删除接口 |
| F-11 | 后台用户和订单 | 用户查询管理、订单查询、发货和物流维护 | 后端管理员角色校验；角色变更属于更高权限操作 |
| F-12 | 审计 | 记录重要管理操作并支持管理员查询 | 审计内容及筛选条件以审计接口实现为准 |
| F-13 | 媒体 | 管理端上传图片/媒体，页面显示商品图片 | 文件保存在项目 uploads 目录并由媒体路由提供访问 |

## 5 非功能需求

1. **安全性**：密码不得以明文存储；JWT 密钥和第三方私钥通过环境或本地受忽略配置注入；服务端必须执行用户归属和管理员角色校验。
2. **数据一致性**：订单、支付、退款和抽奖的数据库变更应通过事务及条件更新保护；重复支付通知不得重复推进订单或触发重复抽奖。
3. **并发安全**：库存操作结合 Redisson 锁、Redis 辅助计数和 MySQL 条件扣减，防止并发超卖；最终库存以数据库状态为准。
4. **可维护性**：前端按页面、API、Store、组件拆分；后端按 Controller、Service、Mapper 分层。
5. **可用性**：前端显示加载、空数据、错误和权限提示；接口返回统一响应结构。
6. **可追踪性**：库存流水、订单物流、抽取记录及管理员审计为重要操作提供业务记录。

## 6 约束与验收边界

- 技术版本固定为 Java 17、Spring Boot 4.0.8、MyBatis-Plus 3.5.17，不应为解决功能问题擅自升级或降级。
- 本地数据库端口为 3307、Redis 为 6379；具体凭据不得写入本说明书或 Git。
- 真实支付宝验收需要合法商户配置和可达回调；本地模拟支付不能替代该验收。
- 已知数据库的歌曲试听地址为示例链接或空值，当前真实可播放歌曲数为 0/10。应补充有授权的音源后再验收播放。
- Playwright、接口测试和构建结果应引用最新测试报告，不得把历史通过结果当作当前环境的实时测试。

## 7 验收建议

验收至少覆盖：用户注册登录与越权访问；专辑浏览、购物车、地址、订单及模拟支付；管理员发货和用户确认收货；退款申请和审核；盲盒创建订单、付款、结果与记录；库存不足、重复支付、非法状态迁移等异常；页面构建、浏览器控制台、网络请求及移动端布局。涉及数据库写入时使用隔离的测试账号和测试数据，不清理现有业务数据。

## 8 角色用例详细说明

### 8.1 注册与登录

**参与者：** 未登录访问者。  
**前置条件：** 后端可用，注册接口开放，用户名未被占用。  
**主流程：** 用户打开注册页，填写用户名、密码及页面要求的资料；前端先校验必填项、格式和密码确认；提交后端；后端再次校验唯一性、字段约束并按项目当前密码机制保存；成功后只提示注册成功并引导到登录页。用户输入凭据登录，后端验证成功后返回真实 Token 和用户资料，前端才建立登录状态。  
**异常流程：** 用户名已存在、参数非法、密码不匹配或网络不可用时显示服务端/前端错误，不伪造登录成功。  
**验收点：** 注册成功后不自动伪造 Token；刷新页面后状态按实际存储策略恢复；退出后受保护页面不能继续访问。

### 8.2 专辑检索与详情

**参与者：** 已登录用户。  
**前置条件：** 专辑数据可查询，JWT 有效。  
**主流程：** 首页或专辑区域请求真实列表，用户通过搜索/筛选定位商品，打开详情查看价格、库存、商品形态、封面和已关联曲目；如果选择数字专辑，页面只展示有权限公开的信息。  
**异常流程：** 空列表显示空状态；请求被拒绝提示重新登录；详情 ID 无效显示未找到/业务错误；媒体加载失败显示图片占位，不编造商品信息。  
**验收点：** 浏览器 Network 的请求地址、方法及参数与 Controller 一致；页面显示字段来自响应而非硬编码样例。

### 8.3 购物车与地址管理

购物车用于保存用户准备购买的商品与数量。用户可以查看条目、改变数量、选择或移除条目；下单前端提交选择信息，后端仍需重新读取商品价格、库存和状态，不信任客户端传来的金额。地址管理支持用户维护自己的地址；所有更改均应以当前 Token 对应用户为边界。下单时后端核实地址仍存在、有效且属于该用户，然后把收件人和地址复制到订单快照。地址后来修改不应覆盖已创建订单的历史地址。

### 8.4 创建订单、支付和履约

用户提交订单后，系统检查商品和地址，扣减/预留库存，创建待支付订单和订单明细快照。支付页面创建支付流水，用户在本地演示环境选择模拟支付。支付成功后订单由后端状态处理器推进；重复通知不能重复完成后续业务。管理员对符合条件的实物订单填写物流，系统记录物流并变更状态。用户只能对本人且已发货的订单确认收货。未支付订单可取消或超时关闭，并按服务逻辑回补库存。

### 8.5 退款

用户选择本人订单并提交原因，服务端重新评估订单状态、商品类型、数字内容是否访问及是否已有重复申请。已发货实物申请还需要退货承运信息。管理员审核时需核对订单、支付和退款申请的一致性。拒绝操作不得错误地把订单标记为已退款；批准操作应关联实际支付渠道。模拟支付订单只完成本地状态流转，不能宣称资金已返还。

### 8.6 盲盒

用户查看盲盒与奖池说明，选择单抽或十连抽，并提供本人有效地址。创建订单只保留购买名额并生成待支付单。支付成功事件触发后端抽取，结果和抽取时概率被持久化，页面随后读取本人记录。用户不能通过浏览器传入中奖奖品 ID，也不能跳过支付直接要求服务端产生付费抽取结果。

### 8.7 后台管理

后台管理员先通过普通登录接口获得 Token，再由前端显示授权菜单。后台列表支持项目实际接口提供的查询、分页和筛选；编辑表单提交前进行必填与范围校验。新增、编辑、上传、发货、审核等动作均应呈现处理中状态，避免重复点击；收到后端失败响应时保留表单上下文并明确提示。审计页面仅管理员可访问。某资源没有后端删除接口时，前端不能提供看似成功的删除按钮。

## 9 数据项与校验需求

| 数据对象 | 用户可提交的数据 | 服务端必须复核的内容 |
|---|---|---|
| 账户 | 用户名、密码、个人资料 | 格式、唯一性、密码校验、账户状态 |
| 商品查询 | 关键词、分类、页码、页长 | 页码范围、查询条件和权限 |
| 购物车 | 商品 ID、数量、选择状态 | 商品有效性、数量范围、当前用户归属 |
| 地址 | 收件人、电话、地址文本、默认状态 | 必填、格式、归属、可用状态 |
| 订单 | 商品或购物车条目、地址 ID | 服务端价格、库存、商品类型、地址归属 |
| 支付 | 订单或支付单标识 | 当前用户归属、金额、支付状态、回调验签 |
| 退款 | 订单、原因、退货信息 | 退款资格、重复申请、订单/支付当前状态 |
| 盲盒 | 盲盒 ID、次数、地址 ID | 次数限制、上架、库存、地址归属、奖池可用性 |
| 管理写操作 | 表单字段、资源标识 | 管理员角色、字段合法性、目标状态及审计 |

客户端校验用于减少明显错误，但不能取代服务端校验。金额、角色、概率、库存、支付成功和中奖结果等关键字段必须由后端控制。

## 10 接口行为与响应需求

前端通过统一 Axios 实例发起业务请求。应用响应使用项目统一的 `code/message/data` 结构；HTTP 状态和业务码需要分别分析。请求成功但业务码失败时页面仍需显示错误，而不能只判断 HTTP 200。401 代表身份失效，应清理当前登录状态并回到登录流程；403 代表当前身份没有操作权限，应显示拒绝原因；网络断开或超时应保留可重试入口。分页结果应使用后端真实总数和当前页信息。

## 11 异常场景需求矩阵

| 场景 | 预期后端处理 | 预期前端表现 | 数据要求 |
|---|---|---|---|
| 未登录访问受保护资源 | 返回认证失败 | 提示登录并跳转 | 不写入业务记录 |
| 普通用户访问管理员接口 | 返回权限拒绝 | 显示无权限 | 不执行管理操作 |
| 访问他人订单/地址 | 拒绝或按安全策略隐藏资源 | 显示不可访问 | 不泄漏他人字段 |
| 重复点击支付 | 状态条件保护、幂等处理 | 按钮防重复并刷新状态 | 不重复抽奖/扣库存 |
| 库存不足 | 条件扣减失败 | 明确提示库存不足 | 不产生负库存 |
| 无效状态操作 | 业务拒绝 | 显示当前操作不可用 | 状态保持不变 |
| 文件类型/大小不合规 | 拒绝上传 | 显示原因 | 不保存非法资源 |
| 媒体 URL 失效 | 不影响业务数据 | 显示图片占位或播放错误 | 不伪造资源可用 |

## 12 可用性与兼容性要求

桌面端是后台表格和表单的主要使用环境；移动端优先保证导航可打开、内容不横向溢出、按钮易点击和主要用户流程可完成。列表加载应显示清晰状态，空列表应解释如何产生数据或如何重试。输入框应有明确标签和错误文本，弹窗可通过取消退出。颜色不能是表达状态的唯一方式，成功、失败、待处理状态需配合文字。

## 13 验收用例建议

1. 新用户注册后登录，验证错误凭据、重复用户名和退出后状态。
2. 普通用户请求本人及他人订单/地址，确认服务端数据隔离。
3. 添加商品到购物车、改数量、下单，核对订单和明细快照。
4. 模拟支付一次及重复请求，确认只产生一次状态迁移。
5. 管理员发货、用户确认收货，尝试越权确认他人订单。
6. 分别测试数字内容未访问和已访问情况下的退款资格。
7. 盲盒订单单抽和十连抽支付后对照记录数量及保底统计。
8. 提交非法数量、无效地址、下架商品和库存不足请求。
9. 测试图片上传大小/格式错误与实际 URL 展示。
10. 记录浏览器错误、请求状态和数据库只读核验结果。

| 退款 | 退款页面/后台审核 | 规则、事务及渠道 | `refund_application` | 资格与重复申请测试 |
| 盲盒 | 盲盒页面/抽取记录 | 预留库存、抽取、保底 | `blind_box`、`draw_record` | 付款后的记录与库存核验 |
| 管理与审计 | 后台各页 | 角色校验、审计记录 | `admin_audit_log` | 普通用户越权和审计查询 |

## 15 需求变更管理

新增业务应先明确用户角色、触发条件、请求字段、状态变化、并发场景和数据库影响，再更新接口文档、迁移脚本、前后端实现及测试。需求变更不得直接通过前端假数据绕过后端规则。涉及数据库字段或索引时应准备向前兼容迁移、备份计划及回滚说明；涉及支付或退款时先使用模拟环境与沙箱环境验证。

## 16 详细用例规格

### UC-01 普通用户创建专辑订单

**目标：** 用户购买一个或多个当前允许销售的商品。  
**参与者：** 已登录用户、订单服务、库存服务、MySQL。  
**触发：** 用户从商品详情或购物车发起结算。  
**前置条件：** Token 有效；用户未被禁用；商品仍然有效；实物商品有本人有效地址。  
**主成功场景：** 页面提交商品标识、数量和地址标识；后端从身份上下文取得用户 ID；后端重读商品当前状态、价格和库存；按业务规则保护库存；生成订单主记录及商品明细快照；返回订单标识和当前待支付状态；页面进入订单详情。  
**扩展场景：** 若价格在页面展示后变化，服务端应以当前价格为准并按业务约定返回新的订单金额或提示用户重试；库存不足时不生成成功订单；地址失效时提示重新选择；数据库失败时事务不应留下半张订单。  
**后置条件：** 成功时订单可查询且库存变化可追溯；失败时不得伪报成功。  
**验收证据：** HTTP 响应、订单主单、订单明细和库存流水的一致性检查。

### UC-02 用户完成模拟支付

**目标：** 在不发生真实资金交易的开发环境中验证订单付款状态流转。  
**前置条件：** 项目模拟支付配置已开启；当前用户拥有待付款订单。  
**主成功场景：** 前端创建支付流水，取得支付单标识；调用仅限开发环境的模拟支付操作；后端验证支付单用户归属、待支付状态和模拟开关；支付处理成功后推进订单状态；前端重新查询订单和支付状态。  
**拒绝场景：** 模拟支付关闭、订单不归属当前用户、支付单已结束、订单已取消或已经支付时，后端拒绝重复处理。  
**后置条件：** 只记录本地模拟支付状态，不产生真实资金划转。  
**验收证据：** 支付单和订单状态，重复请求后的状态保持，以及交易流水未被误认为真实渠道交易。

### UC-03 管理员发货

**目标：** 将符合条件的实物订单推进到物流履约阶段。  
**参与者：** 管理员、订单服务、审计模块。  
**前置条件：** 操作者有管理员角色；订单处于可发货状态；承运商和物流单号满足输入规则。  
**主成功场景：** 管理员在订单后台检索目标订单；打开发货表单；填写物流信息；前端校验必填项；后端重新校验角色和订单状态；写入物流记录并推进订单状态；生成审计记录；页面刷新订单详情。  
**异常场景：** 普通用户调用管理接口时拒绝；重复发货时条件更新失败；物流单号缺失时参数校验失败；审计查询不能被普通用户访问。  
**验收证据：** 订单新状态、物流记录和审计记录一致。

### UC-04 用户申请退款并由管理员审核

**目标：** 在规则允许时形成可追踪退款申请，并由管理员作出审核。  
**前置条件：** 用户拥有订单；订单和商品状态符合退款策略；如需退货物流则资料齐全。  
**主流程：** 用户提交申请；服务端验证归属、状态、商品类型和是否重复申请；创建待审核记录；管理员查询并打开申请；服务端再次校验管理员角色和申请状态；审核结果写入申请，若批准则执行支付/订单及库存后续处理。  
**边界：** 用户不能审核自己的退款；拒绝不能把订单写为已退款；已访问数字内容按当前规则拒绝在线退款；模拟渠道退款只能说明本地状态模拟。  
**验收证据：** 申请记录、审核人、审核结果、订单/支付状态及库存流水。

### UC-05 用户购买盲盒

**目标：** 用户购买一次或十次盲盒抽取机会并获得可核验结果。  
**前置条件：** 用户登录；盲盒上架；库存充足；用户地址有效；奖池有可用奖品配置。  
**主流程：** 页面加载盲盒真实数据；用户选择次数和地址；后端校验并创建待支付订单、预留库存；用户模拟支付；订单支付成功事务触发后端抽取；后端写每次记录、累计统计和订单摘要；页面读取本人的抽取记录。  
**异常场景：** 未付款不抽取；支付通知重复不重抽；库存不足拒绝；抽取写库失败执行补偿；用户查看他人记录被拒绝。  
**验收证据：** 订单抽数、支付状态、库存变化、抽取记录数、奖品概率快照和保底统计。

## 17 用户界面需求说明

### 17.1 导航和布局

用户端布局应明确品牌、主要导航、登录状态和页脚信息。页面滚动时导航不遮挡主要内容；移动端菜单能展开/收起。管理端侧边栏应根据真实角色显示菜单，但无法访问的路由还要由后端拒绝。当前路由不存在时显示明确的未找到页面及返回入口。

### 17.2 列表与详情

列表应明确当前筛选条件、结果数量、分页、加载和空状态。搜索框提供回车和按钮两种可理解操作方式，重置筛选应清空相关条件并重新请求。详情页面要区分商品说明、价格、库存、歌曲试听和需要登录的操作。无图片时显示统一占位，但不得以占位图替代商品数据本身。

### 17.3 表单和重复提交

表单标签应说明单位、必填项和格式要求；校验错误定位到对应字段。提交时禁用按钮并显示进行中状态，避免重复请求。提交失败保留用户已输入但不泄漏敏感内容。对删除、发货、退款审批等具有明显业务影响的动作，应展示目标对象和操作结果；不存在后端 API 的动作不得显示可用。

### 17.4 无障碍与可读性

按钮和表单控件需有明确可读名称；状态颜色同时提供文字；图片应使用有意义的替代文本；键盘焦点顺序清晰。小屏幕下表格可横向滚动或转换为卡片，不能让主要操作被裁切。

## 18 数据需求细化

### 18.1 用户数据

用户数据只收集完成认证和业务所需的信息。用户名需有唯一性约束或等效校验；密码不得以明文返回；个人资料接口只返回当前用户资料。用户是否启用、是否拥有管理员角色必须由服务端判断，不能相信页面缓存的旧角色。

### 18.2 商品数据

商品至少需要可识别的名称、状态、价格、形态、封面和库存信息。歌曲需要能关联到专辑并包含适当展示字段。商品描述、图片 URL 和音频 URL 需区分用途；不可把数字内容下载地址作为未经授权的公开试听链接返回。

### 18.3 交易数据

订单需要唯一标识、所属用户、状态、金额、业务类型、建立时间与必要履约信息。金额计算由后端按数据库商品价格进行；订单明细保存价格快照；实物地址快照需足以完成历史查证。支付与退款流水需能够追踪到订单，但不能让普通用户通过猜测编号读取他人流水。

### 18.4 盲盒数据

奖池包含可用于展示和抽取的奖品、等级、概率、图片等字段。服务端抽取需保存当次使用的概率，防止日后配置调整改变历史说明。保底统计要与用户、盲盒维度绑定，并有明确的重置规则和可验证记录。

## 19 外部依赖和接口边界

| 外部/基础服务 | 用途 | 缺失时的表现 | 验收方式 |
|---|---|---|---|
| MySQL | 持久化用户及业务数据 | 后端无法完成主要业务查询/写入 | 只读连通检查和 QA 业务验证 |
| Redis | 库存辅助计数与锁 | 并发业务可能失败或不可用 | TCP/认证检查和应用连接日志 |
| 媒体目录 | 图片和音频文件 | URL 404 或无法上传 | 文件存在、HTTP 状态和浏览器展示 |
| 支付渠道 | 沙箱/真实下单及退款 | 真实付款或退款不可验收 | 合法沙箱参数和签名回调 |
| 环境变量 | JWT 密钥等敏感配置 | 应用启动或认证初始化失败 | 只检查是否存在，不输出值 |

## 20 需求优先级及验收覆盖

| 优先级 | 内容 | 选择理由 | 最低验收标准 |
|---|---|---|---|
| P0 | 登录、权限、订单、支付状态、数据归属 | 决定交易安全与核心演示 | 正常、越权、重复及非法状态均验证 |
| P1 | 地址、购物车、退款、盲盒、后台管理 | 覆盖主要业务闭环 | 浏览器实际操作并核对服务端结果 |
| P1 | 图片上传及商品展示 | 影响项目演示完整度 | 实际文件和响应 URL 可访问 |
| P2 | 真实音频试听 | 当前音频数据缺失 | 有授权文件并在浏览器实际播放 |
| P2 | 生产支付、部署监控 | 外部运营条件较多 | 合法外部环境和运维配置验证 |

## 21 验收结果记录格式

每项验收记录至少包含：用例 ID、日期、环境版本、测试用户类型、前置数据、执行步骤、请求路径/方法、HTTP 状态、业务响应、页面结果、数据库只读核验、控制台错误、结论和问题编号。凭据、完整 Token、地址、电话等个人信息不得放入报告。测试未执行、服务不可用或缺少外部凭据时应明确标“未测/受阻”，并给出恢复条件。

## 22 需求分析结论

本项目需求围绕“商品目录—用户选择—订单支付—物流/数字交付—退款或盲盒结果”展开。复杂交易规则以服务端为准，前端负责清晰反馈并按统一响应处理。最终验收须同时看界面、接口和数据，而不是只看页面是否可点击或 Maven 是否编译。已知音频及真实支付边界应在需求范围和答辩中持续保持一致。

## 23 质量属性场景

| 属性 | 场景 | 期望系统行为 | 验证证据 |
|---|---|---|---|
| 安全 | 普通用户请求他人订单 | 服务端校验归属并拒绝，不返回订单内容 | 两个 QA 用户的 API 对照测试 |
| 一致性 | 两个用户同时购买最后一件库存 | 最多一个请求成功，库存不为负数 | 并发集成测试和库存流水 |
| 幂等 | 同一支付成功通知被重复投递 | 状态只推进一次，不重复触发抽取 | 重复通知测试和抽取记录数量 |
| 可恢复 | 数据库写入期间发生异常 | 本地事务回滚，外部预扣走补偿路径 | 故障注入或集成测试日志 |
| 可用性 | 媒体文件不可达 | 页面显示替代状态并可继续浏览其他内容 | Network 404 与 UI 检查 |
| 易用性 | 用户提交表单字段错误 | 错误定位到字段，保留可修正的输入 | 浏览器操作和截图 |
| 可维护性 | 修改接口字段 | API 模块和 DTO 映射集中，测试能定位差异 | 代码审阅与回归结果 |
| 可审计性 | 管理员发货/审核 | 记录操作者和操作路径，查询受权限保护 | 审计记录只读查询 |

具体响应时间、并发数和可用性目标需结合部署资源和课程验收要求确定，当前没有压测数据时不在本文承诺数值。

## 24 需求边界与非目标

为避免验收范围不断扩大，本项目当前不承诺以下内容：

1. **生产级支付平台：** 本地模拟支付不承担清算、对账、拒付和资金安全责任。
2. **真实版权音乐库：** 没有授权文件和真实 URL 时，不视为已实现真实音乐播放。
3. **成熟物流平台集成：** 现有物流信息以管理端填写和订单展示为主，不等同于承运商实时轨迹 API。
4. **完整营销中台：** 会员积分、优惠券、促销规则及推荐算法须另行确认需求。
5. **高可用集群：** 单机开发拓扑不能证明具备多活、自动故障转移和灾备能力。
6. **无限制媒体服务：** 本地 uploads 目录不等同于对象存储/CDN，容量和备份仍需部署方案。

如果后续要求加入这些功能，应更新需求、数据设计、权限、接口和测试，不以口头演示补足缺失实现。

## 26 需求评审问题清单

正式需求评审时应确认：

- 数字商品允许访问几次、访问链接有效期及下载记录的保存方式。
- 实物商品取消、缺货、拆单和部分退款的规则。
- 盲盒奖池概率总和如何校验，奖品库存是否独立于盲盒抽取次数。
- 保底计数跨活动/跨奖池是否延续，奖池变更后如何处理历史累计次数。
- 退款申请时限、客服补充材料和超时自动关闭规则。
- 管理员操作是否需要二次确认及操作审计保留策略。
- 媒体上传的最大体积、允许格式、访问鉴权和文件保留方式。
- 数据库与媒体文件的备份频率、恢复点目标和数据保留期限。

这些规则中未由当前代码或产品决定的部分应标记“待确认”，不可由前端自行推断。
