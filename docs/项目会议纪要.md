## 二 会议目的

本次会议围绕音乐专辑与衍生品发售系统当前实现开展复盘，统一项目范围、关键技术实现、数据与权限边界、系统演示步骤和待完成事项。会议材料需要帮助项目成员说明“页面操作如何转为后端业务、数据最终保存在哪里、关键规则由哪一层保证”，并使答辩内容和代码实现保持一致。

会议同时梳理不可夸大的边界：编译通过不等于所有业务经过真实联调；模拟支付不等于资金交易；播放器控件存在不等于音源可播放；前端管理员菜单不等于服务端权限。后续测试记录应写明执行日期、环境、账号类型、请求结果和数据核验结论。

## 三 项目现状汇报

### 3.1 总体架构

项目使用 Vue 3 + Vite 构建浏览器端页面，使用 Vue Router 管理用户端和后台路由，Pinia 保存登录与播放器状态，Axios 统一调用 `/api` 接口。后端使用 Java 17 和 Spring Boot 4.0.8，通过 Controller 接收请求、Service 执行业务、Mapper 访问 MySQL。MyBatis-Plus 版本为 3.5.17。Redis 与 Redisson 用于并发库存辅助和分布式锁。答辩材料保留该固定版本组合，不因个别环境问题任意改版本。

会议记录确认的讲解顺序是：用户在页面发起操作，前端 API 模块携带认证信息，JWT 拦截器识别当前用户，Controller 进行参数入口校验，Service 执行业务状态和事务，Mapper 更新数据库，统一响应回到 Axios，页面根据真实响应显示结果。任何环节失败时都不能由前端伪造成功状态。

### 3.2 用户端功能

当前前端包含登录、注册、首页/专辑、歌曲、购物车、地址、订单、支付、退款、盲盒和个人信息等页面。注册成功后跳转登录页，不应直接写入虚假的登录状态。登录后才保存接口返回的 Token 与用户资料。购物车当前按单项结算，不应在答辩中说成支持已实现的一键合并结算。

专辑目录和详情由后端接口提供，不应使用固定演示数组替换真实数据。地址、订单和退款等操作以用户身份隔离。前端路由守卫用于改善访问体验，服务端仍须验证 JWT、角色与数据归属。

### 3.3 管理端功能

后台界面提供数据概览、专辑、歌曲、盲盒、用户、订单和审计日志入口。会议要求每个写操作均对照对应 Controller 与 HTTP 方法确认：有后端接口并完成联调的才能展示为可用；没有删除接口时，不应设置假删除按钮。后台新增、编辑、上传、发货和退款审核由服务端做角色校验并记录必要审计信息。

## 四 重点业务讨论

### 4.1 订单和快照

讨论结论：订单不是单纯的“商品 ID + 用户 ID”。创建订单时必须校验商品状态、价格、库存和收货地址归属；历史订单还应保存当时商品和地址的快照。这样目录后续修改不会改变用户已购买的凭证。订单主表表达整笔交易，订单明细保存多商品情形下的名称、封面、数量、单价和商品形态。

在答辩演示中，应展示待支付订单、支付状态变化和实物履约状态。状态改变由后端按原状态条件执行，不允许浏览器任意提交一个目标状态来修改订单。订单超时取消会走业务取消和库存回补流程。

### 4.2 支付和幂等

本地演示使用模拟支付开关。模拟支付只修改本地支付单和订单状态，不向用户、商户或第三方转移资金。真实支付宝渠道依赖商户参数、签名私钥、平台公钥以及可访问的回调地址；当前演示不能把模拟结果说成真实收款。

支付通知存在重复到达的可能。后端使用订单当前状态作为条件推进，只有一次请求能够将待支付订单推进为已支付。重复请求应读取/返回当前结果，不得再次抽奖、重复扣库存或重复发货。答辩时可以解释支付流水和订单履约状态分开存储，前者回答“付款处理如何”，后者回答“商品履约到哪一步”。

### 4.3 盲盒抽取闭环

盲盒前端显示盲盒列表、奖品信息、单抽/十连选择和记录。页面操作调用创建盲盒订单接口，不直接调用一个并不存在的用户抽奖 HTTP 接口，也不在浏览器生成随机奖品。

后端先验证盲盒上架、抽数范围、库存和地址归属，使用锁和库存条件更新预留抽取名额，生成待支付订单。支付成功处理识别盲盒订单后调用服务端抽取逻辑。抽取使用 SecureRandom 和奖池概率，并根据用户统计执行 SR/SSR 保底；每次结果单独写记录，概率按抽取时快照保留，订单保存结果摘要。若未支付取消或过期则释放预留库存。抽取失败需要沿补偿路径处理支付状态和库存，不能只显示“已抽中”而没有持久记录。

会议认为此流程是项目答辩的重点，应画出时序图并解释：创建订单、预扣库存、支付、条件状态更新、抽取、记录落库、前端查记录。明确前端是购买入口和结果展示端，后端是抽取与概率规则的唯一可信执行端。

### 4.4 退款与数字商品

退款资格取决于商品形态、订单状态和数字内容是否已访问。数字商品完成访问后受退款规则限制；实物已发货时需要相应退货物流资料。管理员拒绝退款只改变退款申请结果，不应把订单和支付写成已退款；批准则需要联动退款申请、订单和支付，并按业务情况处理库存。

真实支付渠道退款依赖外部配置和渠道确认。数据库事务可以保护本地多表变更，但不能自动撤销已经完成的外部资金调用。若进入生产化，应增加支付/退款异步对账、重试和人工处理机制。纪要要求验收报告区分“本地模拟状态完成”和“真实退款渠道成功”。

## 五 数据库和运维讨论

### 5.1 核心表组织

主要数据按账户、目录、交易、盲盒和审计分组。账户由 `sys_user` 支持；商品使用 `album` 与 `song`；用户购物与地址使用 `shopping_cart`、`user_address`；交易包括 `order_info`、`order_item`、`payment`、`order_logistics` 和 `refund_application`；盲盒包括盲盒、奖品、抽取记录和用户统计；库存变更与管理操作分别通过库存流水和审计日志追踪。

不同数据库版本可能存在历史迁移。会议要求以当前 `sql/music_system.sql`、日期迁移脚本、Mapper 和数据库实际结构为准；旧版在线学习平台文档中的课程/教师数据模型不属于本系统，不能拷贝进音乐系统说明。

### 5.2 缓存与数据库一致性

Redis/Redisson 解决并发协调和性能辅助问题，MySQL 条件更新承担持久化库存的最终校验。锁、事务和幂等是不同机制：锁限制并发进入；事务维护数据库内多写入的一致性；幂等确保重复请求不重复执行。若发生库存不一致，应先读取库存流水、订单状态和 Redis/数据库计数再诊断，禁止为“恢复正常”直接清缓存或随意更新库存。

### 5.3 数据保护

现有业务库不得清空，不得用初始化脚本覆盖已有数据。迁移前确认数据库名、当前版本、脚本执行历史并备份。QA 账号和订单应使用明确标记，可保留用于复测。任何需要新增数据的操作应确认范围；未批准不得修改现有普通用户角色。迁移失败时先停止后续操作并检查备份，不能以重建库代替排障。

## 六 测试与验收意见

### 6.1 测试分层

- 后端构建：确认当前依赖下 Java 源码可编译。
- 单元测试：覆盖状态策略、退款资格、概率和保底边界。
- 数据访问/集成测试：验证条件更新、事务回滚、库存和快照。
- API 测试：实际检查路径、HTTP 方法、参数、响应结构和权限。
- Playwright：操作真实页面，检查按钮、表单、路由、Console 和 Network。
- 环境测试：检查 MySQL、Redis、JWT、端口和媒体目录。

任何一层通过都不能自动替代其他层。测试报告需要写执行环境与日期，未实际运行的项目写“未测试”。核心业务不能全部 Mock 后就宣称完成真实集成测试。

### 6.2 必测场景

1. 用户登录失败、Token 失效和退出后访问受保护页面。
2. 普通用户请求管理员路由和管理 API，服务端返回拒绝。
3. 用户读取/修改他人订单、地址和退款记录时被阻止。
4. 库存不足、非法数量、地址不归属、下架商品和缺少必填项。
5. 重复支付、重复退款、订单取消后再支付和非法状态迁移。
6. 单抽、十连、保底阈值、库存不足和抽取失败补偿。
7. 商品媒体上传、文件 URL 可访问和列表/详情图片展示。
8. 桌面和移动端排版、表格滚动、弹窗和导航操作。

### 6.3 测试数据原则

测试使用 QA 用户和专用商品/订单；数据应可识别并且操作范围可控。不得用真实支付，除非通过正式批准的沙箱商户凭据完成。不得修改普通用户角色伪造管理员。对于可能产生持久数据的 E2E 测试，提前确认目标数据库并在报告注明留存数据。

## 十一 逐项复盘记录

以下内容以项目当前实现为基础，作为会议讨论记录的扩展稿。若实际会议讨论未涉及某一项，请删除或改为“会后材料”，不要把它当作已发生的口头结论。

### 11.1 前端结构复盘

复盘重点包括 Vue 应用入口、路由配置、状态管理、API 封装、用户布局和后台布局。页面独立拆分能够使业务职责更清晰；共享 Axios 实例可以统一身份头、响应解析和异常提示；Pinia 负责跨页面用户状态和播放器状态。会上建议按“页面组件不直接决定权限、API 模块不猜接口、Store 只保存服务端确认的登录信息”作为代码检查基线。

页面验收应区别三种情况：页面路由能加载、接口能返回、业务写操作最终持久化。只检查第一种不能说明功能完成。前端单元或浏览器测试需要观察 Network 请求，并在写操作后重新读取数据，避免按钮本地修改数组后产生“看起来成功”的假象。

### 11.2 后端结构复盘

后端通过 Controller、DTO、Service、Mapper、Entity 和 VO 分层。会议说明稿要求讲清 Controller 是请求入口，不承载抽奖随机或复杂订单规则；Service 负责校验和事务；Mapper 处理持久化；DTO/VO 用来隔离请求/响应结构。统一异常处理使参数错误和业务冲突能够转换为前端理解的 Result。

代码检查的关注点是：管理员身份是否在后端验证、当前用户 ID 是否来自可信认证上下文、Mapper 更新是否检查影响行数、事务边界是否覆盖需要原子处理的数据库写入。日志应提供问题定位信息，同时避免把认证头和敏感支付参数写入日志。

### 11.3 商品目录和媒体复盘

目录、详情、封面和曲目数据应由接口返回。新增图片应满足文件存在、URL 可访问、记录地址与页面展示一致。若旧商品没有图片，可使用项目允许的原创/免费素材补齐，但需保留来源和许可说明。商品图片与音频文件需分别管理；图片素材可用不能推导歌曲音频也存在。

播放能力复盘时应说明全局播放器接收歌曲对象和试听 URL，Audio 元素实际加载文件后才可以播放。现有 10 首歌曲没有真实可用音源，5 条地址是示例链接、5 条为空，因此真实可播放量为零。后续如添加音源，应记录授权、文件格式、大小、URL 状态码和浏览器实际播放情况。

### 11.4 数据库快照与审计复盘

订单保存地址和商品快照是为了交易历史稳定；支付流水和订单状态分开，是为了分别表示资金处理和商品履约。库存流水用于解释库存变化，抽取记录用于还原奖品结果和概率，管理审计用于确认谁在何时执行了重要操作。这些表不是重复数据，而是面向不同查询和追溯需求。

复盘时建议使用只读方式展示一条 QA 订单的关联记录：订单主单、明细、支付、物流或退款、库存流水。盲盒演示可查看盲盒订单、支付、逐抽记录及用户保底统计。所有查询必须限定 QA 标识，隐藏个人地址、电话、密码摘要和支付敏感内容。

## 十二 重点问题与记录意见

### 12.1 是否所有页面都已完成

不能仅凭路由清单回答“全部完成”。每个页面需要检查是否有真实数据、主要操作、错误与空状态、权限、移动端布局和后端接口。后台某些新增/编辑/删除操作若后端接口没有对应能力，应标记为缺失或未完成，不可用纯前端假操作代替。当前项目报告中已有一部分 Playwright 结果，但最终提交前应按当前代码重新确认是否仍然有效。

### 12.2 是否支持完整真实交易

本地模拟支付用于验证状态流转，不代表支付机构真实收款。真实交易还需商户配置、签名校验、通知地址、渠道对账和退款闭环。正式商户私钥不可写入仓库或会议材料。答辩中可以演示模拟流程并解释接口边界，不需要也不应为了效果执行真实扣款。

### 12.3 是否支持所有商品形态

专辑模型区分数字与实物形态；实物依赖地址快照、发货和物流；数字内容依赖订单权限与访问记录。实际每个商品是否完整配置、数字资源是否真实可下载，应以目标数据库与媒体文件为准。没有验证的资源不能在会议纪要中写为可交付。

### 12.4 是否可直接部署到生产

项目技术上具备本地开发和演示基础，但生产部署还要验证 HTTPS、秘密管理、数据库最小权限、备份恢复、日志监控、上传目录持久化、真实支付渠道、音频版权及并发容量。没有压测和灾备恢复记录时，不应给出“生产级”结论。

## 十六 行动项拆解

### 16.1 环境检查

确认 Java 17、Maven、Node/npm 可用；查看 MySQL 3307 和 Redis 6379 状态；查明 8080 与 5173 是否被占用及进程身份；确认 IDEA 运行进程能获取 JWT_SECRET。检查过程中只报告变量存在状态，不把密钥写进截图。

### 16.2 后端回归

使用项目指定 Maven settings 执行编译；若运行失败，记录第一条真实异常并沿 Bean、配置、数据库或 Redis 依赖定位。只修复与根因相关的配置或代码，不为消除表面错误删除业务逻辑。启动后以真实接口检查登录、列表和测试页面。

### 16.3 数据库检查

确认目标 schema、迁移执行状态和 QA 数据范围。对订单/支付/抽取/退款只读核验，记录关键标识的脱敏形式。若发现缺失字段，先比对迁移脚本，不直接手工创建表；任何写入都需要明确范围并保留可追踪证据。

### 16.4 浏览器检查

运行现有 E2E，用 QA 账号操作关键页面；保存测试结果、Console 及失败请求摘要；核查按钮重复提交、401/403、表单边界、移动端溢出。页面截图不得含密码和 Token。自动化跳过的用例应记录依赖条件，不能写成通过。

## 二十一 会议沟通原则

1. 先陈述可验证事实，再讨论原因；构建、启动、接口和数据库结果分别记录。
2. 汇报缺陷时给出重现步骤、受影响模块和数据风险，不用“应该没问题”代替验证。
3. 对支付、退款、角色变更和数据库迁移明确操作授权与回退方案。
4. 外部依赖未准备好时写清阻塞条件，避免将未完成项藏在“后续完善”一句话中。
5. 讨论技术债时指出当前兼容方案、生产风险和改造优先级，不在答辩材料里隐藏遗留实现。
6. 会议结束前确认每个行动项的责任人、截止日期和可检查的完成标准。
